## 二、发现的真实缺陷与修复

### 2.1 SSRF 防护绕过 ×6（安全）

- 位置：`api/channelRouter.ts` `assertSafeBaseUrl`。
- 缺陷：原实现漏掉 6 类内网变体——`[::1]`、`[0:0:0:0:0:0:0:1]`、`[::ffff:127.0.0.1]`、`[::ffff:7f00:1]`（Node URL 会把点分映射规范化为 hex）、`[fe80::1]`（链路本地）、`localhost.`（尾点）。
- 修复：去方括号 + 去尾点后判定；IPv6 回环 / `fe[89ab]:` 前缀（链路本地）/ IPv4 映射段（hex 解码回环）全拦截。
- 验证：C 组 20 种内网变体全拦截、公网（8.8.8.8 / 公网 IPv6 / 172.32.0.1）放行、update 路径同样拦截。

### 2.2 analysisList 排序内存爆炸（缺陷）

- 位置：`agent.analysisList` 的 `ORDER BY created_at` 叠加 SELECT 大 JSON `payload` 列。
- 缺陷：触发 MySQL filesort 溢出，仅 19 行数据即 500「Out of sort memory」。
- 修复：`db/schema.ts` `analyses` 表新增复合索引 `idx_analyses_source_ref_created(source, passageId, createdAt)`；迁移 `db/migrations/0006_old_morgan_stark.sql`（含顺带无害的 `vocab_items.image MODIFY longtext`）+ `meta/0006_snapshot.json` + `_journal.json`；服务启动 bootstrap 幂等应用。

## 七、经验总结

1. **SSRF 校验的敌人是 URL 规范的「合法写法」**：方括号、尾点、hex 映射、全零压缩、大小写……每条都是独立的绕过面。正确姿势是先规范化（去 `[]`、去尾点）再判定，而不是枚举黑名单。
2. **排序 + 大字段 = filesort 内存炸弹**：`ORDER BY` 一个列 + `SELECT` 一个 4MB JSON 列，MySQL 会把要排序的数据放进内存，行数一多就「Out of sort memory」。归档/列表类查询必须走复合索引。
3. **批量断言比逐条断言省事**：边界测试按「域」分批（A~I），失败即定位到断言名，重跑成本低，一次跑 137 项 ≈ 单个脚本运行。
4. **边界测试应该零 LLM 消耗**：把「校验层拒绝」与「真实调用」分开测——前者可随时全量跑、可进 CI；后者消耗额度、按需跑。两者缺一不可。
5. **文档是版本交付物的一部分**：功能做完了不算完，使用手册/API 清单/测试指南补齐后，下一次维护（人 or AI）的返工成本显著下降。
