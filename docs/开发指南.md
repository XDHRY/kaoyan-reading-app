# 开发指南（纸上功夫 · 从零到交付）

本文档面向**开发者**：覆盖环境搭建、常用命令、数据库迁移流程、编码方法论（PonyTAIL）、提交规范与版本回退。与 `AGENTS.md`（约定速查）、`docs/架构说明.md`（架构）、`docs/测试指南.md`（验收）互为补充。

## 一、环境搭建

### 1.1 前置要求

| 依赖 | 版本 | 说明 |
|------|------|------|
| Node.js | ≥ 20 | 与 Dockerfile `node:20-slim` 一致 |
| MySQL | 8+（或 TiDB） | **必须以 UTC 时区启动**（见下） |
| npm | 随 Node | 依赖已锁定，用 `npm ci` |

### 1.2 数据库（关键：UTC 时区）

时区口径不一致会导致 TIMESTAMP 偏大 8 小时、僵尸任务心跳判定失效（v5.10 根因，详见 `verifier/runs/20260808_v510.md`）。因此：

```bash
# Windows 命令行示例（datadir 可换成你的数据目录）
"C:\Program Files\MySQL\MySQL Server 8.1\bin\mysqld.exe" \
  --datadir=C:\path\to\data --port=3306 \
  --default-time-zone='+00:00' --console
```

创建库并授权：

```sql
CREATE DATABASE kaoyan_reading CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

### 1.3 首次启动

```bash
cp .env.example .env    # 填 DATABASE_URL、APP_ID、APP_SECRET、ADMIN_PASSWORD
npm ci
npm run build           # 前端 vite + 后端 esbuild → dist/boot.js
NODE_ENV=production node dist/boot.js
```

首次启动自动完成：建表（幂等迁移）→ 种子数据（SOP 条款/真题语料/预置渠道）→ 管理员账号（`ADMIN_PASSWORD` 指定；未指定则打印一次随机密码）。

> 生产建议：`ADMIN_PASSWORD` 必须显式设置；`APP_SECRET` 用足够长的随机串（JWT 签名用）。

## 二、常用命令

```bash
npm run dev          # 前端 vite 开发服务器（后端用 npm start 另起）
npm run build        # 生产构建 → dist/boot.js
npm start            # NODE_ENV=production node dist/boot.js
npm run check        # tsc -b 类型检查（门禁）
npm run lint         # eslint（门禁）
npm test             # vitest 单测
npm run db:generate  # 改 schema.ts 后生成迁移
npm run format       # prettier --write .
```

交付门禁三绿：`check` + `lint` + `build`，再加全量回归（见 `docs/测试指南.md`）。

## 三、数据库迁移流程

1. 改 `db/schema.ts`（单一事实源）；
2. `npx drizzle-kit generate --name <描述性名字>` 生成 `db/migrations/00xx_*.sql` 与 `meta/` 快照；
3. 服务启动时 `bootstrap` 自动幂等应用（`__drizzle_migrations` 记账）——**无需手工迁移**，老部署升级即自愈；
4. 铁律：**绝不修改已应用的历史迁移文件**；需要变更就生成新迁移；
5. 若同时修改了索引/大字段，注意同步 `_journal.json` 与 `meta/00xx_snapshot.json`（drizzle-kit 自动处理，不要手改）。

> 经验（v5.11）：`ORDER BY` 大 JSON 列会触发 MySQL filesort 内存溢出，归档类排序务必建复合索引（如 `idx_analyses_source_ref_created`）。

## 四、编码方法论（PonyTAIL 懒惰阶梯）

本项目采用 GitHub 上 PonyTAIL 的方法论（「让 AI 像最懒的资深程序员一样思考」——**最好的代码是没写的代码**）。写代码前按阶梯自问：

1. **需要存在吗？**——YAGNI。不存在的需求、不变化的配置、未来才用的抽象，一律不建。
2. **代码库里已有？**——先 grep 复用，不要在共享函数外另写一份。
3. **标准库 / 平台原生够吗？**——不引第三方依赖。
4. **已装依赖能用吗？**——项目已依赖的库（zod/drizzle/hono…）优先。
5. **一行能写就写一行**——最短 diff、最少文件。
6. **Bug 修根因**——grep 所有调用者，在共享函数修一次，而不是到处打补丁。

配套纪律：

- **不建多余抽象**：一个实现的接口、一个产品的工厂、没有第二个使用者的「可复用组件」都不要；
- **删除优先于添加**：删掉死代码/无用配置的收益大于加注释；
- 有意简化处加 `ponytail:` 注释说明「为什么够用、上限在哪、升级路径是什么」；
- 输出代码优先，解释最多三行；理解不能懒——先读透再动手；
- 非平凡逻辑留一个最小可运行自检（不引测试框架，`verifier/v1/*.py` 或内联脚本皆可）。

> 反面教材（本项目历史）：多余抽象（为单一用途建工厂）、到处打补丁（同一校验多处复制）都造成了返工。遵循阶梯后，v5.11 的 SSRF 修复只改了一个函数（`assertSafeBaseUrl`）、analysisList 只加了一个索引。

## 五、提交规范

- 消息格式：`类型: 摘要 — 要点`，如 `chore: 发布 v5.11.0 — SSRF 防护加固 + analysisList 排序修复 + 边界测试 137 项 + 文档扩充`；
- 类型：`fix:`（缺陷）/ `feat:`（功能）/ `chore:`（版本/工程）/ `docs:`（文档）/ `ci:` / `verifier:`（测试与验收）;
- 提交前 `git status` 复核：`.env`、`db/dump_parts/`、`__pycache__/` 等绝不允许入库；
- 一次提交 = 一个逻辑变更（本轮边界测试脚本、迁移、源码修复、文档可同版提交，但消息要写全）；
- 版本号规则：每个功能版本（`v5.x`）必须全量回归通过才允许升版 + 打 tag。

## 六、版本与回退

### 6.1 发布流程

1. 全量回归全绿 + 门禁三绿；
2. `package.json` 升版本号；
3. `CHANGELOG.md` 顶部加版本条目（引用验收记录）；
4. `verifier/runs/` 写验收记录；
5. commit + 打 tag（`git tag v5.11.0`）+ push（tag 随 push）。

### 6.2 回退

```bash
git tag                     # 列出所有版本 tag
git checkout v5.10.0        # 回退到上一个版本（detached 或新建分支）
# 或用任意提交 SHA：
git log --oneline
git checkout <sha>
```

回退后数据库：老代码启动时只应用「老代码自己的迁移」，不会回滚表结构；如需同步数据基线，用 `db/dump.tar.gz` 还原（见 README「完整数据库快照」）。

## 七、调试技巧

- **直查数据库**：`verifier/v1/test_boundary_v6.py` 里的 `dbq(sql)` 通过项目根 `node` + `mysql2` 直查 MySQL（自动读 `.env` 的 `DATABASE_URL`），改 SQL 即可复用；
- **看渠道请求日志**：LLM 请求失败看服务端 stdout；渠道「测试」按钮返回的 message 已带原因；
- **限流干扰测试**：`api/lib/rate.ts` 内存窗口，撞 429 就重启服务；
- **构建产物**：`dist/boot.js` 是单文件全量产物，`node dist/boot.js` 直接可跑，无需再装依赖。
